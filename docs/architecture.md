# Архитектура PharmaQC

Версия 3.0.0. Документ описывает текущую реализацию, а не исходный план.

## 1. Границы системы

**Вход:** HTTP-вопрос на русском языке, 1–1000 символов.

**Выход:** JSON с ответом, документами-источниками, чанками, временем обработки и флагами `refused` / `partial`.

**Данные:** пять учебных TXT-регламентов и метаданные. Персональные данные для работы не нужны.

**Внешние зависимости:** local-режим не имеет внешних runtime-зависимостей; groq-режим зависит от HuggingFace при первой загрузке e5 и от Groq API при каждой генерации.

## 2. Общая схема

```text
                         ┌──────────────────────────────┐
HTTP client ───────────▶ │ FastAPI + Pydantic           │
                         │ /health, /api/v1/ask         │
                         └──────────────┬───────────────┘
                                        │ PharmaQCService.ask()
                         ┌──────────────▼───────────────┐
                         │ Выбор PHARMAQC_ENGINE        │
                         └──────────┬───────────┬───────┘
                                    │           │
                               local│           │groq
                                    │           │
                 ┌──────────────────▼──┐   ┌────▼────────────────────┐
                 │ LocalRAGPipeline    │   │ RAGPipeline             │
                 │ JSONL → BM25        │   │ e5 → ChromaDB           │
                 │ multi-query + guard │   │ top-k + threshold       │
                 │ extractive answer   │   │ Groq JSON + retry       │
                 └──────────────────┬──┘   │ quote grounding         │
                                    │      └────┬────────────────────┘
                                    └───────────┘
                                                │
                                     ┌──────────▼──────────┐
                                     │ QueryResponse       │
                                     │ answer/sources/...  │
                                     └─────────────────────┘
```

## 3. Local-контур

### Retrieval

1. Вопрос и чанки нормализуются: нижний регистр, `ё→е`, единые дефисы, простое сведение словоформ.
2. `rank_bm25.BM25Okapi` ранжирует 61 чанк.
3. Baseline использует только исходный запрос.
4. Improved добавляет подзапросы для самостоятельных аспектов: условия исследования, критерии/статус/действия, классификация/регистрация/расследование, ре-квалификация, хранение документации.
5. Победитель каждого подзапроса включается в retrieved set; в ответ идут только фрагменты, прошедшие retrieval.

### Контроль ответа

- **Object guard:** если идентифицирующая пара слов объекта отсутствует в корпусе и лучший фрагмент имеет слабое покрытие вопроса, сервис отказывается отвечать.
- **General rule:** для ре-квалификации конкретного оборудования и срока хранения конкретных протоколов ответ получает оговорку и `partial=true`.
- **Numeric rule:** значение процента из вопроса сравнивается только с явно найденным допуском `±N%`; вывод о превышении добавляется отдельно.
- **Источники:** формируются из answer chunks, а не из всех найденных документов.

Local-режим не вызывает LLM. Ответ представляет собой дословные фрагменты с ограниченной детерминированной композицией.

## 4. Groq-контур

1. `embed.py` создаёт e5-эмбеддинги с префиксом `passage:`.
2. `index.py` сохраняет их в ChromaDB с cosine distance.
3. `RAGPipeline.retrieve` кодирует вопрос с `query:` и отбирает top-k с порогом 0.75.
4. Контекст и вопрос помещаются в разные защищённые разделители.
5. Groq возвращает JSON: `status=answer|general_rule|no_info`, `answer`, `quote`.
6. Каждая часть цитаты проверяется в контексте. При неподтверждении сервис возвращает отказ, а не непроверенный ответ.
7. 429 и временные ошибки повторяются с задержкой; фатальные ошибки не повторяются.

## 5. API и ошибки

| Слой | Ситуация | Поведение |
|---|---|---|
| Pydantic | Пустой/длинный/неверный вопрос | HTTP 422, сервис не вызывается |
| Service | RAG не инициализирован | HTTP 503 |
| Groq | LLM недоступна после попыток | HTTP 503, общий текст клиенту |
| Groq | Некорректный JSON после попыток | HTTP 502 |
| FastAPI | Непредвиденная ошибка | HTTP 500 без внутренних деталей |
| Любой | Ответа нет в базе | HTTP 200, `refused=true`, пустые `sources` |

Синхронная обработка вызывается через `run_in_threadpool`, чтобы не блокировать event loop.

## 6. Конфигурация и секреты

- `config/app.yaml` — пути, local, retrieval, embeddings, ChromaDB, LLM, API, логирование.
- `config/presets/baseline.yaml` и `improved.yaml` — воспроизводимые сравнения.
- `PHARMAQC_ENGINE=local|groq` — выбор контура.
- `GROQ_API_KEY` — только для groq; не записывается в код и логи.
- `CORS_ORIGINS` — опциональный allowlist; по умолчанию CORS отключён.

## 7. Логирование

Записываются запуск, выбранный движок, число чанков, длина вопроса, число результатов, статус отказа и latency. Текст вопроса и ответ не логируются. В ошибках LLM сохраняется класс исключения, но секретный текст не передаётся клиенту.

## 8. Развёртывание

- Local: готовый `chunks.jsonl` входит в проект, Uvicorn/Docker запускают сервис без предварительного индексирования.
- Groq: сначала `main.py → chunk.py → embed.py → index.py`, затем запуск; `data/` монтируется в контейнер.
- `/health` используется Docker healthcheck.

## 9. Известные ограничения

Доменные intent-правила local-режима требуют расширения вместе с новыми типами вопросов. Лексический BM25 слабее semantic retrieval при сильной перефразировке. В groq-режиме остаются внешняя задержка, стоимость и зависимость от доступности провайдера. Для production нужны авторизация, контроль доступа к документам, аудит версий и мониторинг качества.
