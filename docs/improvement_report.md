# Отчёт о доработке и сравнении качества

## 1. Метод сравнения

Для итогового зачётного сравнения использованы две воспроизводимые конфигурации одного локального RAG:

- **baseline** — один BM25-запрос, top-k=3, ответ по одному лучшему фрагменту, без object guard и оговорок;
- **improved** — исходный запрос + аспектные подзапросы, до трёх дословных фрагментов, проверка объекта вопроса, partial-оговорки и сравнение числового допуска.

Общие условия: один `data/chunks/chunks.jsonl` (61 чанк), один `data/test_questions.json` (10 вопросов), одинаковый код оценки, 3 прогона каждой конфигурации. Пресеты находятся в `config/presets/`.

Архивные Groq-замеры в `data/eval/archive_before_fixes/` сохранены как история исходного проекта, но **не используются в основной таблице**: часть формулировок и типов вопросов была уточнена, поэтому смешивание этих результатов нарушало бы требование сравнивать версии на одинаковых сценариях.

## 3. Посценарный анализ

| Вопрос | Проблема baseline | Решение improved | Итог |
|---|---|---|---|
| Q5 | Один лучший чанк не содержал допуск и действия | Три аспектных подзапроса: критерии, статус, несоответствие; сравнение 3% с ±2% | PASS |
| Q6 | Общее правило выдавалось без оговорки | `general_rule`, `partial=true`, явное «отдельное указание не найдено» | PASS |
| Q7 | Ответ по слабо связанному фрагменту | Проверка пары слов, идентифицирующей объект; «инъекционных растворов» нет в корпусе | PASS |
| Q9 | Не хватало действий и сроков | Подзапросы для классификации, немедленных действий и расследования | PASS |
| Q10 | Не было оговорки и нужного общего срока | Отдельный подзапрос по хранению документации валидации + partial | PASS |

Q1–Q4 и Q8 корректно решались обеими версиями; это контрольные случаи, показывающие, что доработка не сломала исходные успешные сценарии.

## 4. Другие исправления исходного проекта

| Область | Изменение |
|---|---|
| Чанкинг | Нумерованные пункты сохраняются целиком; регрессионный тест проверяет отсутствие потерь на всех пяти регламентах |
| Конфигурация | Единый `config/app.yaml`, пресеты baseline/improved, выбор движка через `PHARMAQC_ENGINE` |
| Groq-ответ | JSON `status/answer/quote`, проверка цитаты, источники только по подтверждающим чанкам |
| Ошибки | Пустой ответ и невалидный JSON повторяются; 503/502/500 не возвращаются как обычный текст ответа |
| Безопасность | Ключи только в окружении; текст вопроса не логируется; служебные теги удаляются; CORS выключен |
| Проверка | 66 автотестов, 4 HTTP smoke-сценария, детерминированный замер качества |

## 5. Ручной просмотр итоговых ответов

Все 10 ответов improved просмотрены по детальным JSON:

- Q1–Q4, Q8 содержат требуемые значения и названия документов;
- Q5 логически корректно заключает, что 3% превышает ±2%, и приводит красную маркировку, изоляцию, отклонение и расследование;
- Q6 и Q10 явно отделяют общее правило от отсутствующего отдельного указания;
- Q7 отказывается без подстановки температуры из исследования стабильности;
- Q9 объединяет класс, первые действия, 24 часа и 30 календарных дней.

Некоторые ответы содержат соседние пункты регламента сверх минимально необходимого. Это не влияет на корректность, но является кандидатом на дальнейшее сокращение extractive-композиции.

## 6. Выводы и ограничения

Содержательное улучшение подтверждено заранее выбранной метрикой accuracy и дополнительными метриками на одинаковых данных. Основной вклад дают не только параметры top-k, а мультизапросы и правила безопасной композиции ответа.

Однако выборка мала и частично использовалась при разработке правил, поэтому 100% является результатом на учебном наборе, а не доказательством обобщающей способности. Следующий этап — независимый набор из 50–100 вопросов, новые формулировки, больше no_answer и сравнение с гибридным dense+BM25 reranking.

Качество Groq-режима в этой среде не измерялось из-за отсутствия API-ключа. Local-метрики не должны приписываться LLM-режиму.
